# light-view 설계 문서

작성일: 2026-10-26
상태: 검토 반영본 (사용자 최종 승인 대기)

표기: **[사용자 결정]**은 사용자가 대화에서 직접 정한 것, **[설계자 판단]**은 대화 중 제안했고 사용자가 반대하지 않은 기본값이다. 아무 표시가 없는 항목은 위 두 가지를 풀어 쓴 요구사항이다.

## 1. 무엇을, 왜

윈도우에서 HEIC(아이폰 사진)를 보려면 마이크로소프트의 유료 HEVC 확장이 필요하고, 반디뷰 같은 뷰어도 HEIC를 유료 기능으로 묶어 두었다. light-view는 **HEIC를 포함한 일상 사진을 무료로, 빠르게, 안전하게 여는 가벼운 윈도우 이미지 뷰어**다. 오픈소스로 공개하고 무료로 배포한다. **[사용자 결정]**

쓰는 장면 **[사용자 결정]**: 탐색기에서 사진을 더블클릭하면 바로 열리고, 좌우로 넘기면서 같은 폴더의 사진을 훑어본다. 필요하면 확대해서 보고, 돌려서 저장하고, 지우고, EXIF를 확인한다.

### 반디뷰의 실패에서 배운 것

사용자가 반디뷰 v7.25~v8.03 변경 기록을 근거로 "이런 문제가 안 생기게 미리 고민해서 만들자"고 했다. **[사용자 결정]** 기록에서 반복되는 문제 다섯 가지와 우리의 대응:

| 반디뷰에서 반복된 문제 | light-view의 대응 (상세는 해당 절) |
|---|---|
| HEIF·AVIF·RAW·JXR·메타정보 처리의 보안 취약점(임의 코드 실행 포함) | 메모리 안전 언어, C 디코더 최소화와 격리, 지원 형식 최소화, 퍼징 (§6) |
| 대형 이미지를 확대할 때 비정상 종료 | 디코딩 전 크기 검사, 메모리 상한, 타일 렌더링 (§5.3) |
| 긴 경로 파일 삭제 실패, NAS에서 다른 파일이 열림, 주소 표시줄을 끌어 놓으면 폴더가 휴지통으로 감 | 파일 정체성 재확인, 긴 경로 지원, 삭제 대상은 화면에 보이는 파일 하나뿐 (§5.4) |
| 일부 HEIC가 안 보이거나 SDR 색이 틀림 | 색 관리(ICC/nclx → sRGB), 실제 기기 샘플 테스트 묶음 (§5.2, §8) |
| 최대화 시작, 테두리 숨김 시 잘림, 일부 창에 다크 모드 누락 | 창 상태 테스트 항목화, 모든 창에 처음부터 다크 모드 (§4, §8) |

## 2. 목표, 비목표, 반목표

### 목표 (v1)
- 탐색기 더블클릭 → 첫 화면이 체감 지연 없이 뜬다 (§7 성능 목표).
- 같은 폴더 안에서 이전·다음 사진으로 끊김 없이 넘긴다.
- 확대·축소·이동.
- 회전 후 **화질 손실 없이** 원본에 저장한다. 저장 전에 한 번 확인을 거친다. **[사용자 결정]**
- 휴지통으로 삭제하고 실행 취소할 수 있다. **[사용자 결정: 삭제 기능]**, **[설계자 판단: 확인창 대신 실행 취소]**
- EXIF 조회. **[사용자 결정]**
- 다른 PC에 배포 가능한 설치 파일과 포터블 버전. **[사용자 결정]**

### 비목표 (v1에 넣지 않음, 나중에 검토 가능)
- 편집(자르기, 보정, 채도 등), 형식 변환, 인쇄
- 썸네일 목록, 라이브러리·북마크 관리, 압축 파일 안의 이미지 보기
- RAW·DNG·PSD·JXR·JXL·AVIF·SVG·HDR 이미지 (공격 표면을 늘리는 형식은 수요가 확인되면 하나씩 추가)
- HDR 출력, 톤 매핑
- 웹툰(세로 스크롤) 보기

### 반목표 (기술적으로 돌아가도 이렇게 되면 실패)
- 더블클릭하고 기다리는 느낌이 든다.
- 조작된 이미지 파일 하나로 코드가 실행되거나, 뷰어가 통째로 죽는다.
- 사용자가 의도하지 않은 파일이나 폴더가 지워지거나 덮어써진다.
- 회전 저장으로 화질이 떨어지거나, 저장 중 실패해서 원본이 깨진다.
- 사용 기록 수집, 광고, 묻지 않는 네트워크 통신.
- 실행할 때마다 "Windows의 PC 보호" 경고가 뜬다(서명 없는 배포).

## 3. 기술 기반 **[설계자 판단]**

- **언어: Rust.** 메모리 안전성이 보안 목표의 핵심이다. 이 PC에 Rust 1.95와 Visual Studio(MSVC)가 이미 있다.
- **창·렌더링:** 네이티브 Win32 + Direct2D 계열(`windows` 크레이트). 시작 속도, 다크 모드 제목 표시줄, 고DPI, 큰 이미지 타일 렌더링을 직접 다룰 수 있는 가장 가벼운 길이다. 구체적인 그래픽 API 조합(Direct2D 단독, DirectComposition 병행 등)은 빌더 재량.
- **디코더:**
  - JPEG, PNG, GIF, WebP, BMP: 순수 Rust 디코더(`image` 크레이트 계열, JPEG은 zune-jpeg 등). 앱 프로세스 안에서 디코딩한다.
  - HEIC/HEIF: libheif + libde265 (C/C++). 인코더(x265 등)는 넣지 않는다. LGPL 의무를 지키도록 **DLL로 동적 링크**하고 앱 폴더에만 둔다(§9).
  - JPEG 무손실 회전: libjpeg-turbo의 무손실 변환(transupp). 디코딩(표시)은 순수 Rust로 하고, 회전 저장에만 쓴다(§5.6). C 라이브러리는 이 둘(libheif 계열, libjpeg-turbo)뿐이다.
- **EXIF:** 순수 Rust 파서(kamadak-exif 등). HEIC의 EXIF 블록은 libheif에서 원시 바이트만 꺼내 같은 Rust 파서로 해석한다.
- **색 관리:** 순수 Rust CMS(qcms 등)로 이미지의 ICC 프로파일 또는 HEIF nclx 색 정보를 sRGB로 변환한다. 모니터 프로파일 반영은 v1 비목표.

## 4. 화면과 조작

시안: `.superpowers/brainstorm/882-1792973546/content/layout-v2.html` (A안의 몰입감 + C안의 goodflow 색). **[사용자 결정]**

### 4.1 생김새
- **goodflow 「형광펜」 디자인 언어**를 따른다. 따뜻한 종이 바탕, 먹 글자, 형광펜은 채움 전용으로 한 화면에 하나만 쓴다. **[사용자 결정]** 토큰은 goodflow-app-design 스킬의 `references/tokens.md`가 기준이다.
  - 라이트: paper `#FBFAF6`, surface `#FFFFFF`, ink `#1C1B19`, ink2 `#69655D`, hairline `#E9E6DE`, 형광펜(라임) `#D6F04A`, wash `#EDF8AE`
  - 다크: paper `#131311`, surface `#1E1D1A`, ink `#F3F1EA`, ink2 `#A7A399`, hairline `#2A2925`, 형광펜 `#0F766E`, wash `#15524C`. 다크에서는 그림자 대신 hairline으로 면을 띄운다.
  - 형광펜 위 글자는 onHighlighter(라이트 `#1C1B19`, 다크 `#F3F1EA`). 형광펜을 글자색으로 쓰지 않는다.
  - 순번 같은 큰 숫자는 시스템 세리프체, 나머지는 시스템 UI 서체(Segoe UI / 맑은 고딕). 폰트는 번들하지 않는다.
- 라이트·다크는 윈도우 앱 모드 설정을 따르고, 실행 중에 바뀌어도 즉시 반영한다. 제목 표시줄, 메뉴, 대화상자, 알림을 포함해 **모든 창**에 적용한다.
- 사진 바탕색은 paper다. 투명 이미지는 paper 위에 그린다(격자 배경은 비목표).

### 4.2 몰입형 기본 상태 **[사용자 결정]**
- 평소에는 사진과 얇은 제목 줄(파일 이름, 순번 `12 / 128`, 저장 안 된 회전이 있으면 wash 알약 "회전됨 · 저장 안 됨")만 보인다.
- 마우스를 움직이면 화면 아래 가운데에 알약 모양 버튼 줄이 사진 위에 뜬다. 2초 동안 마우스가 멈추면 사라진다. **[설계자 판단: 2초]** 마우스가 버튼 줄 위에 있으면 사라지지 않는다.
- 버튼 순서: `‹` 순번 `›` · `−` `＋` · `↺` `↻` · (저장 안 된 회전이 있을 때만) 형광펜 **저장** · `ⓘ` · `🗑` · `📌`
- 모든 아이콘 버튼은 접근성 이름과 툴팁(단축키 포함)을 가진다. 히트 영역은 44 DIP 이상.

### 4.3 메뉴 고정 **[사용자 결정]**
- 📌을 켜면 버튼 줄이 창 아래에 붙박이 막대로 고정되고, 사진 영역은 그 위 공간에 맞춰진다(사진을 가리지 않는다).
- 고정 상태에서는 막대 양옆에 해상도·용량(왼쪽), 배율(오른쪽)도 보여 준다. 창이 좁으면 이 정보는 숨긴다.
- 고정 여부는 설정에 저장해 다음 실행에도 유지한다.

### 4.3a 메뉴, 설정, 빈 시작 화면 **[설계자 판단]**
- 버튼 줄은 사용자가 정한 그대로 두고, 그 밖의 기능은 **사진 위 오른쪽 클릭 메뉴**에 모은다: 열기(Ctrl+O), 폴더에서 보기, 경로 복사, 기본 앱 설정 열기, 설정(Ctrl+,), 정보(버전·라이선스).
- 파일 없이 실행하면(시작 메뉴 등) 빈 화면에 "사진을 끌어다 놓거나 열어 주세요" 한 줄과 형광펜 **열기** 버튼을 보여 준다. 열기는 윈도우 기본 파일 대화상자를 쓴다.
- 설정은 별도의 작은 창으로 연다(goodflow 언어, 다크 모드 적용). 단축키 편집 UI의 v1 포함 여부는 빌더 재량.

### 4.4 키와 마우스 **[설계자 판단, 사용자 확인 "완벽스"]**
| 입력 | 동작 |
|---|---|
| ← / → , 마우스 휠 | 이전 / 다음 사진 |
| Ctrl+휠, + / − | 확대 / 축소 (마우스 휠은 포인터 위치 기준, 키는 화면 중심 기준) |
| 더블클릭 | 화면 맞춤 ↔ 원본 크기(100%) 전환 |
| 확대 상태에서 끌기 | 사진 이동 |
| Ctrl+← / Ctrl+→ | 왼쪽 / 오른쪽 90° 회전 **[사용자 결정]** |
| Ctrl+S | 회전 저장 |
| Delete | 휴지통으로 보내기 |
| Ctrl+Z | 마지막 삭제 되돌리기 |
| I | EXIF 카드 열기 / 닫기 |
| F11, Enter | 전체 화면 |
| Esc | 전체 화면이면 해제, 아니면 창 닫기 |

- 단축키는 나중에 설정에서 바꿀 수 있게 구조를 잡되, 설정 화면 자체는 v1에서 단축키 편집을 빼도 된다(빌더 재량).
- 폴더의 처음·끝에서 더 넘기면 멈춘다(순환하지 않는다). **[설계자 판단]**

### 4.5 처음 열 때의 배율 **[설계자 판단]**
- 창보다 큰 사진은 창에 맞춰 축소하고, 창보다 작은 사진은 원본 크기(100%)로 가운데에 둔다.
- 이전·다음으로 넘기면 배율은 다시 이 규칙으로 돌아간다.

### 4.6 EXIF 카드
- `I` 또는 `ⓘ`를 누르면 창 오른쪽 위에 surface 카드로 뜬다(사진 위에 겹친다).
- 표시 내용: 촬영 날짜(세리프체로 크게), 시각 · 카메라 기종, 노출(셔터 · 조리개 · ISO, wash 바탕), 해상도 · 용량, GPS 좌표(있을 때만, 좌표 텍스트만, 지도 연동 없음).
- "전체 보기"를 누르면 모든 태그를 이름·값 목록으로 보여 준다. 값은 복사할 수 있다.
- EXIF가 없으면 "EXIF 정보가 없어요"와 파일 정보(해상도·용량·수정 날짜)만 보여 준다.

### 4.7 알림(토스트)
- 먹 바탕을 뒤집은 토스트를 왼쪽 아래에 띄운다. 행동 버튼은 형광펜 알약이다(예: "휴지통으로 옮겼어요 [실행 취소]").
- 문구는 해요체로 짧게 쓰고, 사용자가 할 일을 말한다.

### 4.8 창
- 고DPI(모니터별 DPI) 대응.
- 창 위치·크기·최대화 상태를 기억하고, 그 상태로 다시 연다. 최대화 상태로 시작해도 레이아웃이 정상이어야 한다.
- 이미 창이 열려 있을 때 탐색기에서 다른 사진을 더블클릭하면 **기존 창에서 연다**. **[설계자 판단]** 설정에서 "새 창으로 열기"로 바꿀 수 있다.

### 4.9 언어
- 한국어와 영어. 윈도우 표시 언어를 따른다. **[설계자 판단]**

## 5. 동작 상세

### 5.1 폴더 탐색
- 연 파일이 있는 폴더의 지원 형식 파일을 **탐색기와 같은 순서(자연 정렬, `StrCmpLogicalW` 기준)**로 나열한다. 다른 정렬은 v1 비목표.
- 사진을 보는 도중에 폴더 내용이 바뀌면(파일 추가·삭제·이름 변경) 목록을 갱신하되, 지금 보고 있는 사진은 그대로 유지한다.
- 목록은 **전체 경로 + 파일 정체성(§5.4)**으로 관리한다. 순번(인덱스)만으로 파일을 찾지 않는다.
- 이전·다음 사진을 미리 디코딩한다. 기본은 진행 방향으로 1장 이상, 반대 방향으로 1장이다. 미리 읽는 개수는 메모리 상한 안에서 빌더 재량이다.
- 빠르게 연속으로 넘길 때는 마지막 요청만 끝까지 디코딩하고, 이미 지나간 요청은 취소한다.

### 5.2 디코딩과 색
- 지원 형식(v1): JPEG, PNG, GIF(애니메이션 재생), WebP(애니메이션 재생), BMP, HEIC/HEIF. 확장자가 아니라 파일 시그니처로 형식을 판별한다.
- 방향:
  - JPEG 등은 EXIF Orientation을 반영해 표시한다.
  - HEIF는 컨테이너의 `irot`/`imir` 변환을 반영한다. HEIF 안 EXIF의 Orientation은 다시 적용하지 않는다(이중 회전 금지).
- 색: 내장 ICC 프로파일 또는 nclx 정보가 있으면 sRGB로 변환해 표시한다. 아이폰 Display P3 사진이 sRGB 모니터에서 원본과 비슷한 색으로 보여야 한다.
- HEIC 특수 경우:
  - 여러 장이 든 HEIC(연사 등)는 주 이미지만 보여 준다.
  - 알파 채널을 지원한다.
  - 깊이 맵, 게인 맵, 썸네일 등 보조 이미지는 무시한다.
  - Ultra HDR 게인 맵도 무시하고 SDR 기본 이미지만 보여 준다.
- 열 수 없는 파일은 화면 가운데에 "이 사진은 열 수 없어요"와 파일 이름을 보여 주고, 계속 넘길 수 있게 한다. 앱은 절대 죽지 않는다.

### 5.3 큰 이미지와 메모리
- 디코딩 **전에** 헤더로 해상도를 확인한다.
- 디코딩 결과(픽셀 버퍼)의 메모리 상한을 둔다. 기본값은 빌더 재량이며, 시스템 메모리에 비례해 정하고 설정에서 바꿀 수 있다.
- 상한을 넘는 이미지:
  - 축소 디코딩이 되는 형식(JPEG의 DCT 스케일링 등)은 축소본으로 연다.
  - 안 되는 형식은 "너무 커서 열 수 없어요(상한 N MP)"로 안내한다. 이 경우에도 죽지 않는다.
- 그래픽 장치의 최대 텍스처 크기를 넘는 이미지는 타일로 나눠 그린다. 축소 표시할 때는 미리 만든 축소본(밉맵)을 써서 계단 현상과 과부하를 막는다.
- 확대 상한은 3200%(32배), 축소 하한은 화면 맞춤과 5% 중 작은 값이다. **[설계자 판단]**

### 5.4 파일 안전 (삭제·저장 공통)
- **파일 정체성:** 파일을 열 때 볼륨 일련번호 + 파일 ID(`GetFileInformationByHandle`), 크기, 수정 시각을 기록한다. 삭제나 저장을 실행하기 직전에 같은 경로에서 이 값들을 다시 읽어, 하나라도 다르면 작업을 멈추고 "파일이 바뀌었어요, 다시 열어 주세요"를 안내한다. NAS·네트워크 드라이브처럼 파일 ID가 불안정한 곳에서는 크기 + 수정 시각 + 경로로 대신 확인한다.
- **긴 경로:** 앱 매니페스트에 `longPathAware`를 넣고, 내부 경로는 확장 경로(`\\?\`, UNC는 `\\?\UNC\`)로 다룬다. 260자를 넘는 경로와 네트워크 경로(UNC, 매핑 드라이브)에서 열기·삭제·저장을 모두 테스트한다.
- **삭제 대상:** 지금 화면에 표시된 이미지 파일 하나뿐이다.
  - 폴더는 어떤 경로로도 삭제하지 않는다.
  - 끌어 놓기(드래그 앤 드롭)는 "그 파일·폴더를 열기"로만 처리하고, 이동이나 삭제를 일으키지 않는다.
  - 폴더를 끌어 놓으면 그 폴더의 첫 사진을 연다.

### 5.5 삭제
- Delete 또는 🗑 → 확인창 없이 즉시 **휴지통으로** 보내고, 다음 사진(마지막이었으면 이전 사진)을 보여 준다. 토스트 "휴지통으로 옮겼어요 [실행 취소]"를 약 6초 띄운다. **[설계자 판단]**
- 실행 취소(토스트 버튼 또는 Ctrl+Z)는 파일을 원래 위치·이름으로 되돌리고 그 사진을 다시 보여 준다. 되돌리기는 이번 실행에서 마지막으로 지운 파일 하나에 대해 보장한다.
- 구현 방식은 빌더 재량이다.
  - 휴지통에서 복원하는 방식이든, 토스트가 사라지거나 다른 동작이 일어날 때까지 실제 휴지통 이동을 미루는 방식이든 된다.
  - 미루는 방식이면 앱이 비정상 종료돼도 파일은 **남아 있는 쪽**이어야 한다(안전한 방향으로 실패).
- 휴지통이 없는 위치(일부 네트워크 드라이브, 이동식 미디어)에서는 영구 삭제가 된다. 이 경우에만 "이 위치는 휴지통이 없어 영구 삭제돼요. 삭제할까요?" 확인창을 띄운다.
- 읽기 전용 파일이나 권한이 없는 파일은 사유를 알려 주고 아무것도 바꾸지 않는다.

### 5.6 회전과 저장 **[사용자 결정: 저장 전 확인]**
- Ctrl+← / Ctrl+→(또는 ↺ ↻)는 화면에서만 돌린다. 여러 번 누르면 누적되고, 360°가 되면 "저장 안 됨" 상태가 풀린다.
- 저장하지 않은 회전이 있는 채로 다른 사진으로 넘기거나, 창을 닫거나, 삭제하려 하면 "회전한 내용을 저장할까요? [저장] [저장 안 함] [취소]"를 묻는다.
  - 대화상자에 "다음부터 묻지 않고 바로 저장" 체크를 둔다. 설정에서 되돌릴 수 있다. **[설계자 판단]**
  - 대화상자의 기본 단추(Enter)는 [저장]이다.
- Ctrl+S 또는 형광펜 **저장** 버튼은 묻지 않고 바로 저장한다.
- **무손실 원칙:** 픽셀을 다시 압축하지 않는다.
  - JPEG: **픽셀 자체를 무손실로 돌린다.** **[사용자 결정]** 다시 압축하지 않고 DCT 계수를 재배치하는 jpegtran 방식이다. 태그를 무시하는 프로그램이나 업로드 사이트에서도 돌린 방향으로 보이게 하려는 것이다.
    - 구현은 libjpeg-turbo의 무손실 변환(transupp)을 쓰고, **HEIC 디코더와 같은 격리된 작업자 프로세스 안에서** 실행한다(§6.1). 앱 프로세스에는 C 코드를 늘리지 않는다. **[설계자 판단]**
    - 변환 후 EXIF Orientation은 1(정방향)로 맞추고, EXIF의 가로·세로 크기 태그를 바꾼다. EXIF 썸네일이 있으면 같이 돌리거나 지운다. 그 밖의 메타데이터(EXIF, ICC, XMP, IPTC, 기타 APPn 세그먼트)는 모두 그대로 옮긴다.
    - 저장할 때의 실제 회전량은 "기존 EXIF Orientation + 사용자가 돌린 만큼"이다. 화면에 보이는 그대로 저장돼야 한다.
    - 가로·세로가 MCU 크기(보통 8 또는 16픽셀)의 배수가 아니면 가장자리 블록을 무손실로 돌릴 수 없다. 아이폰 4032×3024 등 대부분의 카메라 사진은 배수라서 문제가 없다. 배수가 아닐 때는 가장자리를 잘라 내지 않는다. 대신 픽셀은 그대로 두고 EXIF Orientation만 바꿔서 저장하고(이것도 무손실), 토스트로 "이 사진은 회전 정보로 저장했어요"라고 알린다. **[설계자 판단]**
  - HEIC/HEIF: 주 이미지의 `irot` 속성을 바꾸거나 추가한다. 압축 데이터는 바이트 그대로 둔다. 속성을 추가해서 메타 박스 크기가 바뀌면 `iloc` 오프셋 등 영향받는 값을 정확히 고친다. HEIF 안 EXIF Orientation이 1이 아니면 1로 맞춰 이중 회전을 막는다. 이 수정은 Rust로 작성한 ISO BMFF 박스 편집 코드가 맡는다.
  - PNG, BMP, GIF, WebP: v1에서는 회전 저장을 지원하지 않는다. 회전 표시는 되지만 저장을 누르면 "이 형식은 아직 회전 저장을 지원하지 않아요"를 안내한다. **[설계자 판단]**
- **원자적 저장:**
  1. 같은 폴더의 임시 파일에 쓴다.
  2. 디스크에 확실히 기록(flush)한다.
  3. 다시 읽어서 디코딩이 되는지 검증한다.
  4. `ReplaceFileW` 등으로 원본과 교체한다.
  - 어느 단계에서 실패해도 원본은 그대로 남고 임시 파일은 정리한다.
- **수정 날짜 유지:** 저장 후 원본의 만든 날짜와 수정 날짜를 원래 값으로 되돌린다. 날짜순 정렬이 회전 때문에 섞이지 않게 하려는 것이다. **[설계자 판단]**
- 저장 직전에 §5.4의 파일 정체성 확인을 한다.

## 6. 보안 **[사용자 결정: "보안관련 이슈 챙겨주고"]**

### 6.1 신뢰할 수 없는 입력 다루기
- 모든 이미지 파일은 공격자가 만든 파일일 수 있다고 가정한다.
- 앱 코드, EXIF 파서, 박스 편집 코드는 Rust로 쓰고 `unsafe`를 최소화한다. `unsafe`는 Win32/FFI 경계로 한정하고, 쓰는 곳마다 사유를 주석으로 단다.
- **C 코드(HEIC 디코딩, JPEG 무손실 회전)는 모두 별도 작업자 프로세스에서 실행한다.** **[설계자 판단]**
  - 앱 시작 시 미리 띄워 둬서 첫 HEIC 열기 지연을 없앤다.
  - 작업자 프로세스는 Job Object(메모리 상한, 자식 프로세스 금지)와 낮은 무결성 수준, 가능하면 AppContainer로 권한을 줄인다. 파일 내용은 앱이 열어서 넘기고, 작업자는 디스크·네트워크에 접근하지 않는다.
  - 작업자가 죽거나 시간 초과되면 그 파일만 "열 수 없어요"로 처리하고 작업자를 다시 띄운다.
  - 격리 수준의 세부 조합은 빌더 재량이지만, "작업자가 망가져도 앱은 살아 있고 사용자 파일은 안전하다"는 결과는 지켜야 한다.
- libheif의 보안 한도(최대 이미지 크기, 최대 아이템 수 등)를 명시적으로 설정한다.
- 지원 형식 목록을 짧게 유지한다. 새 형식 추가는 공격 표면 추가로 보고 따로 검토한다.

### 6.2 DLL과 실행 환경
- 시작하자마자 `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_APPLICATION_DIR)`를 호출해, 앱 폴더와 System32 밖의 DLL을 읽지 않게 한다(DLL 하이재킹 방지).
- 사용자별 설치 폴더(`%LOCALAPPDATA%\Programs\light-view`)에 둔다. 설치 프로그램 자체도 DLL 하이재킹에 안전한 도구로 만든다.

### 6.3 공급망과 의존성
- GitHub Actions에서 `cargo audit` / `cargo deny`(취약점·라이선스)를 매 빌드마다 돌린다. Dependabot을 켠다.
- libheif·libde265·libjpeg-turbo는 버전을 고정해서 소스로 빌드하고(vcpkg 매니페스트 등), 보안 공지를 추적한다. 취약점이 공개되면 패치 릴리스를 낸다.
- 릴리스 빌드는 CI에서만 만든다. 재현 가능한 빌드를 목표로 한다.

### 6.4 퍼징
- cargo-fuzz로 다음을 퍼징한다: (1) 형식 판별 + 각 디코더 진입점, (2) EXIF 파서, (3) JPEG/HEIF 회전 저장 편집 코드, (4) HEIC 작업자 프로토콜.
- CI에서 정기 실행(예: 주 1회, 일정 시간)한다. 발견된 크래시 입력은 회귀 테스트로 고정한다.

### 6.5 코드 서명
- 유료 서명은 쓰지 않는다. 오픈소스용 무료 서명인 **SignPath Foundation**에 신청해 exe, DLL, 설치 파일에 서명한다. **[사용자 결정]**
- 승인 전 릴리스는 서명 없이 내고 SmartScreen 경고를 감수한다. **[사용자 결정]** README에 경고를 넘기는 방법과 SHA-256 체크섬 확인 방법을 적는다. 그래서 §2 반목표 중 "서명 없는 배포 경고"는 SignPath 승인 이후의 목표다.
- CI 릴리스 파이프라인은 처음부터 서명 단계를 끼울 수 있는 구조로 만든다. 승인이 나면 설정만 추가하면 되게 한다.

### 6.6 네트워크와 개인정보
- 네트워크 통신은 업데이트 확인 하나뿐이다. 첫 실행 때 켤지 묻고, 설정에서 끌 수 있다.
  - 방식: HTTPS로 GitHub Releases API를 조회해 새 버전이 있으면 알려 주기만 한다.
  - 다운로드는 사용자가 누르면 브라우저로 릴리스 페이지를 연다. v1에는 앱 안 자동 다운로드·자동 설치가 없다.
- 사용 기록 수집, 광고, 크래시 자동 전송은 없다.
- 크래시가 나면 로컬에 덤프와 로그를 남긴다. 사용자가 원하면 GitHub 이슈에 직접 첨부한다.

## 7. 성능 목표
기준 PC: 최근 5년 안의 일반 노트북(4코어 이상, SSD).
- 더블클릭 → 첫 픽셀: 12MP JPEG **200ms 이하**, 12MP HEIC **400ms 이하**. **[설계자 판단]**
- 미리 디코딩된 다음 사진으로 넘기기: 한 프레임(16ms) 안에 화면 전환.
- 실행 중 메모리: 12MP 사진을 볼 때 300MB 이하.
- 설치 크기: 30MB 이하.
- 측정용 벤치마크를 저장소에 두고 CI에서 큰 퇴행을 잡는다.

## 8. 테스트
- **HEIC 샘플 묶음:**
  - 아이폰 여러 세대(가로·세로·셀피·연사·라이브포토·인물 모드·HDR) 사진
  - 갤럭시 HEIF
  - 알파 채널이 있는 HEIF
  - `irot`/`imir`가 들어간 파일
  - 일부러 깨뜨린 파일
  - 라이선스상 공개해도 되는 샘플만 저장소에 넣고, 나머지는 로컬에서만 쓴다.
  - 사용자가 실제 아이폰·갤럭시 샘플을 제공하고, 실제 아이폰과 NAS·네트워크 드라이브 테스트 환경도 제공한다. **[사용자 결정]** 개인 사진이 섞일 수 있으므로 제공받은 샘플은 저장소 밖(예: `.gitignore`된 `testdata/private/`)에 둔다.
- **회전 저장:** 형식별·방향별로 4번 돌려 저장하면 원본과 압축 데이터가 바이트 단위로 같아야 한다. 저장한 파일을 윈도우 사진 앱, 크롬, 아이폰에서 열어 방향이 맞는지 확인한다.
- **파일 안전:** 260자 초과 경로, UNC/NAS 경로, 읽기 전용 파일, 보는 중에 바깥에서 파일이 바뀐 경우, 휴지통 없는 드라이브, 폴더 끌어 놓기.
- **창:** 최대화 상태로 시작, 다중 모니터 DPI 이동, 전체 화면 전환, 메뉴 고정 켬/끔, 라이트/다크 실시간 전환.
- **큰 이미지:** 상한 직전·직후 크기, 텍스처 한계를 넘는 크기(예: 30000×20000), 아주 가늘고 긴 이미지.
- 순수 로직(정렬, 정체성 비교, 박스 편집, 배율 계산)은 단위 테스트로 고정한다.

  - libheif·libde265는 LGPL-3.0이므로 DLL로 동적 링크하고, 사용자가 같은 이름의 DLL로 교체해 쓸 수 있게 둔다.
  - libjpeg-turbo는 BSD 계열(IJG/BSD-3-Clause/zlib) 라이선스다. 고지문만 `THIRD_PARTY_NOTICES`에 넣으면 되고, 정적 링크해도 된다.
  - 라이선스 전문과 해당 소스 버전 링크를 `THIRD_PARTY_NOTICES`에 넣고, 설치 파일과 포터블 zip에 함께 넣는다.
  - 다른 의존 크레이트의 라이선스도 `cargo about` 등으로 자동 수집한다.
- **HEVC 특허:** HEVC에는 특허 풀이 있다. 비상업 무료 배포에서 문제가 된 사례는 드물지만 위험이 0은 아니다. README에 이 사실을 적는다. (법률 자문 아님)
- **설치 파일:**
  - 관리자 권한 없이 사용자별로 설치한다.
  - 설치 도구는 Inno Setup 사용자별 모드를 기본안으로 하고, 다른 도구도 같은 요건을 채우면 빌더 재량이다.
  - 설치 시 할 일:
    - 지원 확장자에 대한 "연결 프로그램" 등록(HKCU)
    - 시작 메뉴 바로가기
    - 제거 프로그램 등록
  - 윈도우 10/11은 프로그램이 스스로 기본 앱이 될 수 없다. 설치 마지막 화면과 앱 설정에 "기본 앱 설정 열기" 버튼을 두고, 설정 앱의 light-view 기본 앱 페이지를 연다.
- **포터블:** zip으로 배포하며 설정은 exe 옆 폴더에 저장한다. 레지스트리는 건드리지 않는다.
- **설정 파일:** 설치판은 `%APPDATA%\light-view\settings.toml`에 저장한다. 깨진 설정 파일은 백업해 두고 기본값으로 시작한다.
- **배포 경로:** GitHub Releases가 기본이다. winget 매니페스트 등록은 v1 이후.
- **대상 OS:** Windows 10 22H2 이상, Windows 11, x64. ARM64 빌드는 v1 이후. **[설계자 판단]**
