# light-view 웹사이트 설계: 소개·내려받기·릴리스 노트, 광고 자리

- 날짜: 2026-10-31
- 바탕: [light-view 설계](2026-10-26-light-view-design.md), v0.2.0 배포(서명 없음), SignPath Foundation 신청 중(2026-10-31). 조사 요약은 [사이트 조사](2026-10-31-light-view-site-research.md).
- 표시: **[사용자 결정]**은 사용자가 정한 것, **[설계자 판단]**은 제가 정하고 사용자 확인을 기다리는 것, **[사용자 결정 필요]**는 사용자만 정할 수 있는 것, 표시 없는 세부는 빌더 재량.
- 범위: 이 문서와 계획서는 설계까지다. 사이트를 공개하거나(배포, GitHub Pages·Cloudflare 켜기) 계정을 만드는 일은 사용자 확인 뒤에 한다.

## 1. 무엇을, 왜

지금 light-view를 받으려면 GitHub 저장소의 README(한국어, 개발자용 내용이 많다)와 Releases 화면을 거쳐야 한다. 일반 사용자, 특히 "아이폰 사진이 윈도우에서 안 열린다"로 검색해 오는 사람에게는 너무 멀다. 그래서 한 화면에서 **무엇인지 알고, 한 번 눌러 받고, 무엇이 바뀌었는지 읽는** 공개 사이트를 만든다. 광고(Google AdSense 등)를 붙일 자리는 처음부터 설계에 넣되, 광고가 내려받기 버튼처럼 보이는 일은 구조로 막는다. **[사용자 결정: 랜딩·다운로드·릴리스 노트, 광고 자리]**

## 2. 목표, 비목표, 반목표

### 목표
- 첫 화면에서 한 문장 소개 + 형광펜 내려받기 버튼 하나(최신 설치판, 버전·크기 표시) + 요구 사항(Windows 10 22H2 이상 / 11, x64).
- 내려받기 페이지: 설치판 두 방식 표, 포터블판, SHA-256 값과 확인 방법, SmartScreen 안내, 서명 상태, 이전 버전 링크.
- 릴리스 노트: 버전마다 한 페이지, 목록 페이지, 한국어·영어.
- **SignPath 조건 충족:** 모든 페이지 바닥글과 홈·내려받기·릴리스 페이지 본문에 "Code signing policy" 링크, 전용 페이지에 SignPath 문구·역할·개인정보 방침(§7).
- 한국어(기본)와 영어, 라이트·다크, 휴대폰 폭에서도 읽힌다.
- 릴리스를 게시하면 사이트가 사람 손 없이 새 버전·노트·체크섬으로 바뀐다.
- 광고는 켜고 끌 수 있는 설정 하나로, 기본은 꺼짐.

### 비목표 **[설계자 판단]**
- 사이트에서 파일을 직접 호스팅하기(내려받기는 늘 GitHub Releases의 원본 파일로 링크한다).
- 블로그·포럼·댓글·계정·뉴스레터.
- 자동 업데이트 서버(앱의 업데이트 확인은 지금처럼 GitHub API).
- 다른 언어(한국어·영어 외), macOS/Linux 안내.

### 반목표 (돌아가도 이러면 실패)
- 광고가 내려받기 버튼·링크로 오인될 수 있다(AdSense 정책 위반이자 사용자 신뢰 손실).
- "내려받기가 곧 시작돼요" 같은 중간 페이지·자동 다운로드·팝업.
- 사이트에 보인 체크섬이 릴리스 파일과 다르다, 또는 초안(draft) 릴리스가 사이트에 새어 나온다.
- "Code signing policy" 문구가 어떤 홈·내려받기·릴리스 페이지에서 빠진다.
- 앱의 개인정보 방침("광고·분석 없음")과 사이트의 광고·쿠키가 한 문서에서 섞여, 앱이 광고를 하는 것처럼 읽힌다.
- 사이트가 외부 글꼴·스크립트를 동의 없이 불러온다(광고를 켜기 전에는 외부 요청 0).

- 후원(GitHub Sponsors 등) 링크는 **[사용자 결정 필요]**. 넣는다면 바닥글과 FAQ에만, 광고 근처에는 두지 않는다(광고 클릭 유도로 읽히지 않게).
- `robots.txt`, `sitemap.xml`, `ads.txt`(광고를 켤 때), Open Graph 이미지(로고 + 한 문장).

### 3.1 첫 화면 (히어로)

```
[로고] light-view                                   한국어 | English
───────────────────────────────────────────────────────────────────
아이폰 사진(HEIC)도 바로 여는
가벼운 무료 Windows 사진 뷰어

  [ 내려받기  ·  설치판 0.2.0 · 4.5 MB ]   ← 형광펜 채움, 화면에 하나
  github.com에서 받아요 · Windows 10 22H2 이상 / 11 (x64)
  포터블 zip · 모든 버전 · 체크섬 · Code signing policy   ← 먹 텍스트 링크
───────────────────────────────────────────────────────────────────
[스크린샷]
```

- 버튼 문구는 결과를 말한다: "내려받기", 아래 줄에 파일 이름의 핵심(설치판·버전·크기)과 출처 호스트(github.com). 버튼은 GitHub 자산 URL로 바로 간다(중간 페이지 없음).
- Windows가 아닌 기기(휴대폰·Mac)로 오면 버튼은 그대로 두고 아래에 "Windows용 프로그램이에요"를 한 줄 더한다(사용자 에이전트 판별은 문구만 바꾸고 링크는 바꾸지 않는다). 판별 스크립트가 없어도 페이지가 완전하다.
- 소개 문구 후보(README 소개에서): "윈도우에서 HEIC(아이폰 사진)를 보려면 유료 HEVC 확장이 필요해요. light-view는 무료로, 빠르게, 안전하게 열어요." 최종 문구는 빌더가 goodflow 문구 규칙(해요체, 짧게, 결과)으로 다듬고 사용자가 확인한다.

### 3.2 기능 6개 (홈)

README와 설계서에서 사용자에게 의미 있는 것만, 각 한 줄 + 작은 그림(스크린샷 조각 또는 아이콘):
1. HEIC/아이폰 사진을 무료로(유료 HEVC 확장 없이)
2. 방향키로 폴더 넘기기, 빠른 첫 화면
3. 무손실 JPEG 회전 저장
4. 휴지통 삭제 + 실행 취소
5. 올리기 좋게 크기 줄이기(위치 정보 제거 기본)
6. 탐색기에서 HEIC 썸네일(설치판) · 사진 해석은 격리된 작업자에서 · 원격 측정 없음

수치(첫 화면 ms 등)는 README "현재 수치"가 한 대 노트북 측정이라 사이트에는 쓰지 않는다. **[설계자 판단]**

## 4. 콘텐츠 출처

| 무엇 | 출처 | 갱신 |
|---|---|---|
| 소개·기능·FAQ 문구 | `site/content/` 마크다운(ko/en). README에서 옮겨 쓰되 사이트용으로 다시 쓴다(README는 개발자 문서) | 사람이 고침 |
| 프로그램 개인정보 방침 | 저장소 `PRIVACY.md`를 빌드 때 그대로 넣음(언어별 절을 나눠서) | 자동 |
| Code signing policy | README `## Code signing policy` 절을 빌드 때 뽑아 넣음(문구가 두 곳에서 어긋나지 않게) | 자동 |
| 버전·날짜·파일·크기·URL | GitHub Releases API(`/repos/hyunwook-kim-goodflow/light-view/releases`), **빌드 때** 받아 `site/data/releases.json` | 릴리스 게시 때 자동 |
| SHA-256 | 각 릴리스의 `SHA256SUMS.txt` 자산을 빌드 때 받아 파싱 | 자동 |
| 릴리스 노트 본문 | 새 파일 `docs/releases/<버전>.md`(한국어·영어 절) — §6 | 릴리스마다 사람이 씀 |
| 스크린샷 | `site/static/img/`, `testdata`의 합성·공개 샘플 사진으로 찍음(개인 사진 금지) | 큰 화면 변경 때 |
| 로고 | `crates/lv-app/res/light-view.png`(파비콘·OG 이미지도 여기서 만듦) | — |

- **API는 빌드 때만 부른다.** 방문자 브라우저가 api.github.com을 부르지 않는다(방문자 IP가 제3자에 가지 않고, 비인증 60회/시 제한도 없다). **[설계자 판단]**
- **초안 제외:** 빌드에서 토큰으로 API를 부르면 초안 릴리스도 보이므로 `draft == false && prerelease == false`만 쓴다. 초안이 섞이면 빌드를 실패시킨다(반목표).
- 체크섬은 `SHA256SUMS.txt`에 적힌 이름과 자산 이름이 모두 맞을 때만 표시하고, 하나라도 없으면 빌드 실패.
- 사이트의 체크섬은 편의 표시다. 문구로 "GitHub 릴리스의 SHA256SUMS.txt와 같아요"라고 원본을 가리킨다.

## 5. 호스팅 **[사용자 결정: Cloudflare Pages, 2026-10-31]**

| | GitHub Pages + 사용자 도메인 | Cloudflare Pages(정적) + 사용자 도메인 **(추천)** |
|---|---|---|
| 비용 | 무료 | 무료 |
| 광고 | GitHub Pages 이용 한도에 "온라인 사업을 운영하는 무료 호스팅으로 쓰지 말 것"이 있다. 오픈소스 소개 페이지의 광고가 여기에 걸리는지는 회색 지대 | 무료 플랜에 상업적 이용 금지 조항이 없다(제3자 비교 기준, 최종 확인 필요) |
| 대역폭 | 월 100 GB 소프트 한도 | 정적 파일 무제한(제3자 자료, 확인 필요) |
| 배포 | Actions에서 `actions/deploy-pages` | Actions에서 빌드 후 `wrangler pages deploy`(API 토큰 시크릿 필요) |
| github.io 주소 | AdSense는 `*.github.io` 하위 주소를 사이트로 받지 않는다는 보고가 많다 → 어차피 사용자 도메인 필요 | 같음(`*.pages.dev`도 마찬가지) |

- **추천: Cloudflare Pages + 사용자 도메인, 빌드는 이 저장소의 GitHub Actions.** 광고를 나중에 켜도 호스팅을 옮길 일이 없다. 광고를 영영 켜지 않는다면 GitHub Pages도 충분하다 — 그래서 사이트는 어느 쪽에도 올릴 수 있는 평범한 정적 파일로 만들고, 배포 단계만 바꿔 끼운다.
- **도메인:** goodflow 도메인이 이미 있다면 하위 주소(예: `lightview.<goodflow 도메인>`)가 가장 싸다. AdSense는 뿌리 도메인을 사이트로 승인받으면 하위 주소에도 같은 게시자 코드로 광고를 낼 수 있다는 것이 일반적 운영 보고다(Google 공식 문서로는 미확인). 새 도메인(예: `lightview.app`)은 따로 산다. **[사용자 결정 필요]**
- **정적 사이트 생성기: Zola** — 단일 Rust 바이너리(Node 의존성 없음, 저장소가 Rust), 다국어·마크다운·`load_data`(JSON)를 기본 지원. 대안은 Astro(Node). CI에서 Zola 바이너리를 버전·SHA-256 고정으로 받는다(ci.yml의 액션 SHA 고정과 같은 원칙). **[설계자 판단]**
- 소스 위치: 이 저장소 `site/`(별도 저장소로 나누면 README·PRIVACY·릴리스 노트를 끌어오기 번거롭다).

## 6. 릴리스 노트 흐름

지금 `release.yml`은 노트를 워크플로 안에 고정 문장(파일 설명 + 체크섬 + 서명·개인정보 문구)으로 만든다. 사람이 쓰는 "무엇이 바뀌었나"가 없다. 바꾼다:

1. 태그를 달기 전에 `docs/releases/<버전>.md`를 쓴다. 형식:
   ```markdown
   ---
   version: 0.3.0
   summary_ko: 탐색기 HEIC 썸네일이 더 빨라졌어요
   summary_en: Faster HEIC thumbnails in Explorer
   ---
   ## 한국어
   ### 새로운 것
   - …
   ### 고친 것
   - …
   ### 알려진 문제
   - …
   ## English
   ### New
   …
   ```
2. `release.yml`의 "Version from tag" 단계가 이 파일이 있는지, `version`이 태그와 같은지 검사한다(없으면 실패 — `package.ps1`이 Cargo.toml 버전을 검사하는 것과 같은 방식).
3. "Create draft release" 단계는 노트를 **이 파일 본문 + 지금의 고정 부분(파일 설명, SHA256SUMS, Code signing policy·개인정보 문구)**으로 만든다. 고정 부분은 지금 문구를 그대로 둔다(SignPath 조건).
4. 사람이 초안을 게시하면(`release: published`) 사이트 워크플로가 돈다. 사이트는 노트 본문을 GitHub 릴리스 본문이 아니라 **저장소의 `docs/releases/<버전>.md`**에서 읽는다(마크다운을 그대로 쓰고 언어 절을 나누기 쉽다). 버전·파일·체크섬은 API에서.
   - 사람이 게시한 이벤트이므로 다른 워크플로를 깨운다(`GITHUB_TOKEN`이 만든 이벤트만 연쇄 실행이 막힌다).
5. 이미 나간 v0.2.0은 노트 파일을 새로 써서 채운다(v0.1.x는 GitHub 릴리스가 없으므로 목록에 넣지 않거나 "GitHub 이전 기록" 한 줄로).

## 7. Code signing policy와 SignPath 조건

SignPath Foundation 약관(https://signpath.org/terms, 2026-10-31 확인)에서 웹사이트에 걸리는 조건:

- "Code signing policy"라는 말을 프로젝트 **홈페이지와 내려받기/릴리스 페이지**에 쓴다(절 제목이나 전용 페이지 링크).
- "Free code signing provided by SignPath.io, certificate by SignPath Foundation" 문구(이름에 링크).
- 팀 역할(커미터·리뷰어, 승인자)과 구성원.
- 개인정보 방침 링크, 또는 "This program will not transfer any information to other networked systems unless specifically requested by the user or the person installing or operating it." 문장.
- 무료 OSS 조건: 프로젝트 기능을 **내려받기 페이지에** 설명한다(→ `/download/` 머리에 두 줄 소개를 둔다).

사이트에서 지키는 방법:
- `/code-signing/`에 README 절을 그대로 넣고(§4), 홈 히어로·`/download/`·`/releases/`·각 `/releases/<버전>/` 본문에 "Code signing policy" 링크를 둔다. 바닥글에도.
- 1.0.0 뒤 내려받기 페이지의 "무결성과 서명" 절(Notepad++의 Integrity & Authenticity 절처럼)에 파일 속성 → 디지털 서명에서 서명자가 "SignPath Foundation"인지 보는 법을 더한다(Super Productivity 방식).
- 서명 전(지금)에는 "신청 중이에요. 승인 전 릴리스는 서명 없이 SHA-256 체크섬만 있어요"를 내려받기 페이지 서명 상태에 그대로 쓴다. 1.0.0(첫 서명 릴리스) 뒤에는 릴리스별로 서명 여부를 표에 표시한다(서명 여부는 노트 파일 머리에 `signed: true`로 적는다 — API로는 알 수 없다).
- 빌드 검사: 생성된 `index.html`, `download/index.html`, `releases/**/index.html`(ko·en)에 "Code signing policy" 문자열과 `/code-signing/` 링크가 있어야 통과.

### 광고와 SignPath 조건의 충돌 검토

- **약관에 광고 금지 조항은 없다.** 약관이 막는 것은 프로그램의 악성코드·PUP, 독점 구성 요소, 상업적 이중 라이선스, 사용자 동의 없는 데이터 전송, 경고 없는 시스템 변경이다. 웹사이트의 광고 자체는 조건 밖이다. (약관 페이지의 행동 강령은 아직 초안이라고 적혀 있어 바뀔 수 있다.)
- **충돌이 될 수 있는 지점 1 — 개인정보 문장:** SignPath 문장은 "이 *프로그램*은 …보내지 않는다"이고 `PRIVACY.md`도 "광고·분석 없음"이다. 사이트가 광고 쿠키를 쓰면 이 둘과 **헷갈리게** 읽힐 수 있다. → `/privacy/`를 "프로그램"과 "이 웹사이트" 두 부분으로 나누고, 사이트 쪽 방침을 따로 쓴다(§8). 프로그램 문장은 그대로 참이다.
- **지점 2 — PUP 인상:** 내려받기 버튼처럼 생긴 광고가 다른 프로그램(번들러, "드라이버 업데이트" 류)을 받게 하면, 사용자는 그것을 light-view가 깐 것으로 여긴다. SignPath의 "PUP 금지"는 프로그램 조건이지만, 서명 인증서 이름(SignPath Foundation)과 함께 평판이 묶인다. → `/download/`에는 광고를 두지 않고(§9), 내려받기 링크는 늘 GitHub 원본 파일로 간다.
- **지점 3 — 승인 심사 중의 변화:** 신청이 진행 중이다. 사이트를 열어도 조건은 위 방식으로 지켜지고, 신청서의 홈페이지 주소가 바뀌면 SignPath에 알려야 할 수 있다. **광고는 서명 승인(1.0.0) 뒤에 켜기를 권한다.** **[설계자 판단]**

## 8. 개인정보·쿠키·분석

- **광고를 켜기 전:** 쿠키 없음, 외부 요청 없음(시스템 글꼴, 외부 CDN 없음, 이미지는 사이트 안). 분석이 필요하면 쿠키 없는 Cloudflare Web Analytics 정도(이것도 외부 스크립트 하나 — **[사용자 결정 필요]**). 기본은 분석 없음. **[설계자 판단]**
- **광고를 켤 때(AdSense):**
  - AdSense 필수 고지: Google 등 제3자가 쿠키로 이전 방문 기반 광고를 보여 준다는 사실, Google 광고 설정(맞춤 광고 끄기) 링크, 다른 광고 업체를 쓰면 그 목록과 거부 방법. → `/privacy/` "이 웹사이트" 절.
  - **EEA·영국·스위스 방문자:** Google 인증 CMP(IAB TCF 연동)가 있어야 맞춤 광고가 나간다(EEA·영국 2024-01-16부터, 스위스 2024-07-31부터). 없으면 비맞춤·제한 광고만. AdSense의 "개인 정보 보호 및 메시지"(Privacy & messaging) 동의 메시지가 인증 CMP라 따로 업체를 쓰지 않아도 된다. → 그것을 쓴다. **[설계자 판단]**
  - 한국: 개인정보 보호법·정보통신망법상 맞춤형(행태) 광고 고지가 필요할 수 있다. 사이트 방침 문구는 출시 전에 사용자가 확인한다(이 문서는 법률 자문이 아니다). **[사용자 결정 필요]**
- 홈에서 VLC·ShareX처럼 "광고·추적 없음"을 말할 때는 **"앱에는"**을 붙인다("앱에는 광고도 추적도 없어요"). 사이트에 광고가 있으면 주어 없는 "광고 없음"은 거짓이 된다.
- 앱의 `PRIVACY.md`는 바꾸지 않는다. 다만 사이트가 생기면 "앱은 사이트에 접속하지 않는다"(업데이트 확인은 지금처럼 api.github.com만)를 사이트 방침에 적는다.

## 9. 광고 자리 — 내려받기 버튼을 절대 흉내 내지 않게

AdSense 정책 근거(https://support.google.com/adsense/answer/48182): 메뉴·탐색·**다운로드 링크로 오인될 수 있는 위치**에 광고를 두지 말 것, 광고를 다른 콘텐츠와 구별되지 않게 꾸미지 말 것, 광고 위 표시는 "광고/Advertisements/Sponsored Links"처럼 오해 없게, 클릭을 부탁하거나 화살표 등으로 시선을 끌지 말 것, 사이트가 다운로드를 시작하거나 거짓 다운로드를 내세우지 말 것.

규칙 **[설계자 판단]**:
1. **내려받기가 있는 화면에는 광고 없음:** `/download/`, 홈 히어로 화면(첫 화면 높이 안), 릴리스 페이지의 파일 표 근처에는 광고를 두지 않는다. 광고 칸과 가장 가까운 내려받기 링크 사이에는 **머리글이 있는 다른 절이 하나 이상** 있어야 한다.
2. **페이지당 광고 1칸**(홈·릴리스 목록·릴리스 상세·FAQ만). 자동 광고(Auto ads)는 쓰지 않는다 — Google이 위치를 고르면 내려받기 버튼 옆에 들어갈 수 있다. 수동 광고 단위만.
3. **표시:** 칸 위에 작은 `ink2` 글자로 "광고"(영어 "Advertisement"). 칸은 `hairline` 테두리 상자, 높이를 미리 잡아 레이아웃이 밀리지 않게(CLS).
4. **형광펜 금지:** 광고 칸과 그 주변에 형광펜(라임) 색을 쓰지 않는다. 사이트의 내려받기 버튼은 늘 라임 채움 + "github.com" 출처 줄이 있어서, 광고 소재가 어떤 모양이든 우리 버튼과 구별된다.
5. **문구 금지:** "광고를 눌러 응원해 주세요" 류 문구, 광고를 가리키는 화살표·애니메이션. 후원 링크는 광고 칸과 떨어진 바닥글·FAQ에만.
6. **광고 소재 거르기:** AdSense 광고 검토 센터와 차단 설정으로 다운로드 유도형·"PC 최적화/드라이버" 류 소재를 막는다(가능한 범위는 계정에서 확인 — **[사용자 결정 필요]**). Notepad++는 다운로드 버튼 바로 위 AdSense 칸에 "Download/Install" 문구의 악성 광고가 반복해 실렸고, 관리자가 매주 손으로 막으며 버튼 아래에 "악성 광고 신고" 링크까지 둔다(조사 문서 참고). 우리는 위치 규칙(1)로 그 상황 자체를 피하고, 광고를 켤 때 광고 칸 아래에 "이상한 광고 신고"(GitHub 이슈 링크) 한 줄을 둔다.
6a. **공식 주소 알리기:** 7-Zip·VLC처럼 이름을 사칭한 검색 광고·비슷한 도메인이 노리는 일이 있다. README·앱 정보 화면·사이트 FAQ에 "공식 사이트는 <도메인>과 github.com/hyunwook-kim-goodflow/light-view뿐"을 적는다.
7. **기본 꺼짐:** `config.toml`의 `ads.enabled = false`, `ads.client = ""`. 꺼져 있으면 광고 스크립트·칸·`ads.txt`가 빌드 결과에 아예 없다.
8. **빌드 검사:** 생성된 HTML에서 광고 칸(`data-ad-slot`)이 `/download/`에 없고, 내려받기 링크(`data-download`)와 같은 `<section>`에 없으며, 페이지당 1개 이하인지 확인한다.

광고 수익에 대한 솔직한 기대: 페이지가 적은 소프트웨어 소개 사이트는 AdSense 심사에서 "가치가 낮은 콘텐츠"로 거절되기도 한다. 승인 확률을 높이려면 FAQ와 "윈도우에서 HEIC 여는 법" 같은 실제 도움말 글이 있어야 한다. 수익은 방문자 수에 비례해 작을 것이다.

## 10. 디자인 — goodflow 「형광펜」

goodflow-app-design 스킬 `references/tokens.md` §7(웹)이 기준이다. **[사용자 결정: goodflow 디자인]**

```css
:root {
  --paper: #FBFAF6; --surface: #FFFFFF; --surface2: #F2F0EA;
  --ink: #1C1B19; --ink2: #69655D; --hairline: #E9E6DE;
  --hl: #D6F04A; --hl-wash: #EEF5BF; --deep: #6F7F1F; --on-hl: #1C1B19;
  --serif: ui-serif, Georgia, serif;
  --sans: "Segoe UI", "Malgun Gothic", "Apple SD Gothic Neo", "Noto Sans KR", system-ui, sans-serif;
  --radius: 18px;
}
@media (prefers-color-scheme: dark) { :root {
  --paper: #131311; --surface: #1E1D1A; --surface2: #2A2925;
  --ink: #F3F1EA; --ink2: #A7A399; --hairline: #2A2925;
  --hl: #0F766E; --on-hl: #F3F1EA; --hl-wash: #15524C; --deep: #5EE0C8;
}}
```

- 바탕 종이, 글자 먹, **형광펜은 채움 전용, 한 화면에 하나 = 내려받기 버튼.** 형광펜을 글자색으로 쓰지 않는다. 링크는 먹 + 밑줄(호버 때 `--hl-wash` 바탕).
- 다크 모드의 형광 채움은 스킬의 최신 규칙(짙은 틸 + 밝은 먹 글자, 4.5:1 이상)을 따른다. 스킬의 웹 CSS 예시(다크에서도 밝은 라임)는 앱 규칙보다 오래된 값이라 쓰지 않는다. **[설계자 판단]**
- 글꼴은 번들·외부 로드 없이 시스템 글꼴(방문자가 대부분 Windows라 Segoe UI·맑은 고딕). 큰 버전 숫자만 세리프.
- 핵심 낱말 하나(예: "무료", "HEIC")에 `<mark>` 형광펜 — 히어로 문장에 한 번만.
- 선택·현재 페이지 표시는 채움이 아니라 먹 밑줄/테두리.
- 다크는 그림자 대신 hairline 테두리.
- 터치 타깃 44px, 키보드 초점 링(먹 2px), `prefers-reduced-motion` 존중(애니메이션은 형광펜 긋기 하나 정도).
- 로고: `crates/lv-app/res/light-view.png`에서 파비콘(32/180/192/512)·OG 이미지(1200×630, 종이 바탕 + 로고 + 한 문장)를 만든다(`scripts/make-icons.py`와 같은 방식으로).
