# light-view M7 설계: 탐색기에서 HEIC 보기 (썸네일, 미리 보기 창)

- 날짜: 2026-10-29
- 바탕: [light-view 설계](2026-10-26-light-view-design.md), M6까지 완료(main, v0.1.1)
- 표시: **[사용자 결정]**은 사용자가 정한 것, **[설계자 판단]**은 대화 중 제가 정하고 사용자가 "ㅇㅇ"로 받아들인 것, 표시 없는 세부는 빌더 재량.

## 1. 무엇을, 왜

Windows는 HEIC/HEIF 썸네일을 그리려면 Microsoft의 유료 HEVC 확장이 필요하다. 그래서 아이폰 사진 폴더를 탐색기로 열면 사진 대신 빈 아이콘(지금은 light-view 파일 아이콘)만 보인다. light-view가 그 자리를 채워, 아이폰 사진도 탐색기에서 JPEG처럼 보이게 한다. **[사용자 결정: 썸네일과 미리 보기 창 둘 다. 자세히(속성)는 관리자 설치가 필요해서 뺌]**

## 2. 목표, 비목표, 반목표

### 목표
- **썸네일:** 탐색기의 목록·큰 아이콘·갤러리 보기에서 HEIC/HEIF가 실제 사진으로 보인다.
- **미리 보기 창:** 탐색기 오른쪽 "미리 보기" 창에서 HEIC/HEIF를 고르면 사진이 크게 보인다.

### 비목표 **[설계자 판단]**
- JPEG·PNG·GIF·BMP·WebP — Windows 10/11이 이미 그린다.
- AVIF·RAW 등 light-view가 열지 않는 형식.
- 포터블판 — 탐색기 등록이 필요하므로 설치판에서만.
- **자세히(속성 처리기)** **[사용자 결정]**: Windows가 HKLM 등록만 읽어 관리자 설치가 필요하고, 다른 사용자·시스템 프로세스에 사용자 폴더의 DLL을 올리게 된다. 사용자별 무관리자 설치(M5)를 지키려고 뺀다. Windows 자체 HEIF 확장이 있으면 그쪽이 보여 줄 수 있다.
- 속성 쓰기, 미리 보기 창 안의 확대·넘기기.

### 반목표 (돌아가도 이러면 실패)
- 이상한(악의적인) HEIC 파일 하나로 탐색기가 죽거나 멈춘다.
- 썸네일을 만들려고 HEVC 디코더(C 코드)가 탐색기 프로세스나 샌드박스 밖에서 돈다.
- 사진 20장 폴더를 열었는데 썸네일이 몇십 초씩 걸리거나 그동안 탐색기가 버벅인다.
- 원본 사진을 고치거나 사진 폴더에 파일을 새로 만든다.
- 제거한 뒤에도 탐색기 등록이 남아 HEIC가 깨진 아이콘이 된다.

## 3. 안전 원칙 **[설계자 판단]**

- **C 코드(libheif·libde265)는 지금처럼 샌드박스 작업자에서만 돈다.** 탐색기 쪽 확장은 순수 Rust이고, 사진 바이트를 작업자에 넘겨 픽셀만 받는다. 작업자는 M2–M6과 같은 격리(낮은 무결성 또는 AppContainer, Job 안에서 태어남, win32k 잠금, 자식 프로세스 금지, 메모리 상한)를 그대로 쓴다.
- 파일 읽기는 탐색기가 넘겨 준 스트림(`IInitializeWithStream`)으로만 한다. 경로를 받아 직접 열지 않는다. 읽는 바이트는 앱의 HEIC 파일 크기 상한을 넘지 않는다.
- 어떤 실패든 "이 파일은 썸네일 없음"으로 끝낸다(탐색기가 아이콘을 대신 보여 준다). 확장 안에서 패닉이 COM 경계를 넘지 않는다.

## 4. 동작

- **썸네일:** 탐색기가 요청한 크기(보통 96–256 px, 큰 아이콘은 최대 1024 px) 이하로 만든다. HEIC 안에 들어 있는 작은 미리 보기 이미지(아이폰은 보통 있음)가 요청 크기 이상이면 그것을 써서 빠르게, 아니면 본 이미지를 줄여서. EXIF·irot 방향을 적용해 바로 선 사진으로. 색은 앱과 같은 sRGB 처리.
- **미리 보기 창:** 창 크기에 맞춰 본 이미지를 줄여 그린다(확대는 안 함). 배경은 Windows 미리 보기 창 배경을 따른다. 여러 장을 빠르게 고르면 마지막 것만 끝까지 만든다.
- **속도:** 썸네일 한 장 목표 300 ms 이내(작은 미리 보기 이미지가 있을 때 100 ms 안팎), 20장 폴더는 몇 초 안에 다 채워진다. 탐색기가 썸네일을 캐시에 넣으므로 두 번째부터는 즉시. 작업자 프로세스를 썸네일마다 새로 띄울지, 잠깐 살려 두고 여러 장에 쓸지는 빌더 재량 — 단, 격리 수준은 같아야 하고 마지막 요청 뒤 몇 초 안에 끝나야 한다.

## 5. 설치와 제거

- 설치판이 HKCU에 COM 등록과 `.heic`·`.heif`의 썸네일·미리 보기 처리기 등록을 넣는다. 확장 DLL은 설치 폴더(`%LOCALAPPDATA%\Programs\light-view`)에 둔다. 작업자 exe와 DLL들은 그 옆에 있으니 그대로 쓴다.
- 제거하면 등록을 모두 지운다. 탐색기가 DLL을 쥐고 있어 지울 수 없으면 다음 로그인 때 지워지게 한다(재부팅 강제는 안 함).
- 등록 뒤 탐색기에 바뀐 연결을 알린다(이미 `ChangesAssociations=yes`). 썸네일 캐시를 지우지는 않는다(README에 "예전 빈 아이콘이 남아 있으면 디스크 정리 > 미리 보기 사진"을 적는다).
- Microsoft HEIF 확장을 이미 설치한 사용자도 있다. 그 경우에도 light-view 등록이 HKCU라 우선하며, 동작은 같다.

## 6. 사용자 결정 기록

- 자세히(속성 처리기)는 뺀다 — 관리자 설치를 피하려고. (2026-10-29)

## 6a. 빌더 확인에서 정한 것 **[설계자 판단]**

- **업데이트·제거 때 탐색기를 닫거나 다시 시작하지 않는다.** 확장 DLL은 버전마다 다른 파일 이름(`lv-shell-<version>.dll`)으로 설치하고 COM 등록을 새 파일로 바꾼다. 쓰던 옛 DLL은 HKCU `RunOnce`로 다음 로그인 때 지운다(관리자 권한 없이 쓸 수 있는 방법). 제거도 같은 방식.
- **AppContainer는 지금처럼 "되면 쓰고 안 되면 낮은 무결성"이다.** 썸네일 호스트(dllhost)나 미리 보기 호스트(prevhost, 낮은 무결성)에서 AppContainer 프로필을 못 만들면 기존 대체 경로(낮은 무결성 + Job + 완화 정책)로 작업자를 띄운다. 작업자 자체를 못 띄우면 썸네일 없음으로 끝낸다.
- **먼저 짧은 스파이크로 확인한다:** HKCU 등록으로 썸네일·미리 보기 처리기가 실제로 불리는지, 각 호스트에서 작업자를 띄울 수 있는지. 스파이크 결과가 이 설계와 다르면 계획 전에 다시 정한다.
- **시험 환경:** 개발 PC에는 Microsoft HEVC 확장이 설치돼 있어 Windows가 이미 HEIC를 그릴 수 있다. light-view 등록이 우선하는지(HKCU) 확인하고, HEVC 확장 없는 환경(다른 사용자 계정·VM) 확인은 사용자 확인 항목으로 둔다.

## 7. 빌더 재량

- 확장 DLL 크레이트 구성(새 `lv-shell` cdylib 등), COM 구현 방식(`windows` 크레이트 `implement`).
- 작업자 요청 형식(새 IPC 요청 `ThumbnailHeif { max_side }` 등)과 작은 미리 보기 이미지 선택 규칙.
- 미리 보기 창 그리기 방식(Direct2D 또는 GDI).
- 테스트 방식: COM 객체를 테스트에서 직접 만들어 부르는 단위 테스트, 그리고 실제 탐색기 확인은 사용자 확인 항목.
